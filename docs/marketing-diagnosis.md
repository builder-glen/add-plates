## 1. 지금 상태

### 1.1 크롤러가 실제로 받는 것

```bash
curl -s https://add-plates.dev
```

응답은 **1,380 바이트**다. `<body>` 안에서 태그를 걷어내고 남는 텍스트는 다음과 같다.

| 항목 | 값 |
|---|---|
| `<body>` 색인 가능 텍스트 | **0 자** |
| `<title>` | `ADD PLATES` (10자) |
| `<h1>` | 없음 |
| `<noscript>` | 없음 |

`<body>` 전체가 `<div id="root"></div>` 하나다. 자바스크립트를 실행하지 않는 크롤러가 이 주소에서
가져갈 수 있는 한국어 텍스트는 **한 글자도 없다.**

### 1.2 `<head>` 감사

| 태그 | 상태 |
|---|---|
| `<html lang="ko">` | **있음** |
| `<title>` | 있음 — `ADD PLATES` |
| `description` | 없음 |
| `canonical` | 없음 |
| `og:title` · `og:description` · `og:image` · `og:url` · `og:type` | **전부 없음** |
| `twitter:card` 계열 | 전부 없음 |
| JSON-LD (구조화 데이터) | 없음 |
| `robots` 메타 | 없음 |

있는 것은 PWA·테마·아이콘 관련 태그뿐이다. **이 앱이 무엇인지 설명하는 태그는 하나도 없다.**

### 1.3 `robots.txt` 와 `sitemap.xml`

둘 다 **파일이 존재하지 않는다.** 그런데 응답은 404가 아니다.

```
GET /robots.txt   → HTTP 200, content-type: text/html, 본문은 index.html
GET /sitemap.xml  → HTTP 200, content-type: text/html, 본문은 index.html
GET /아무거나-없는-주소 → HTTP 200, 본문은 index.html
```

원인은 `wrangler.jsonc` 의 `"not_found_handling": "single-page-application"` 이다. 없는 경로에
`index.html` 을 돌려주도록 되어 있고, 이 규칙에 `robots.txt` 와 `sitemap.xml` 도 걸린다.

두 가지 결과가 따라온다.

- **크롤러는 `robots.txt` 자리에서 HTML 을 받는다.** 대부분의 파서는 해석 불가능한 내용을
  "규칙 없음 = 전부 허용"으로 처리하므로 차단 사고는 아니다. 다만 정상 상태는 아니다.
- **모든 오타 주소가 200 을 돌려준다.** 검색엔진이 말하는 *soft 404* 다. 없는 페이지인데
  "정상"이라고 답하니, 링크를 잘못 적은 주소까지 홈페이지의 중복 문서로 쌓일 수 있다.
  <!-- soft 404 — 내용은 "없는 페이지"인데 HTTP 상태 코드는 200 OK 로 답하는 상태 -->

### 1.5 자바스크립트를 실행해도 보이는 것

여기가 이번 진단에서 가장 중요한 지점이다. **크롤링 문제 이전에 콘텐츠 문제가 있다.**

`src/App.tsx` 의 분기는 이렇다.

```
if (!session) return <LoginScreen />;
```

로그인하지 않은 방문자 — 즉 모든 크롤러 — 에게 이 앱은 **로그인 화면 하나**다.
홈 화면, 종목 204개, 기록 UI, 추이 그래프는 세션 뒤에 있어 공개 표면이 아니다.

렌더링이 완벽하게 성공했다고 가정했을 때 노출되는 텍스트 전량은 다음과 같다.

> LIGHT WEIGHT, BABY!! / sudo add-plate --both-sides
> 종목만 고르면 지난주에 몇 kg 들었는지 같이 떠요. 장갑 낀 손으로 세 탭이면 한 세트 끝.
> Google로 계속하기 / 봉은 조상이 들이주지 않는다.

**총 131자.** 그리고 이 131자 안에

| 단어 | 등장 |
|---|---|
| 운동 | **0회** |
| 기록 | **0회** |
| 헬스 | **0회** |
| 다이어트 | **0회** |

목표 키워드 네 개 중 **하나도 페이지에 없다.** 카피가 나쁜 게 아니다 — `종목`, `kg`, `세트`,
`탭`은 좋은 카피다. 다만 **이미 아는 사람에게 쓴 말**이고, 검색하는 사람이 치는 말이 아니다.

정리하면, 렌더링을 못 해서 못 찾는 게 아니라 **렌더링에 성공해도 찾을 근거가 없다.**

### 1.6 공유 링크 미리보기 — 지금 당장 손해가 나고 있는 곳

`9aea067` 로 공유 기능이 막 나갔다. `navigator.share({ title, text, url })` 로 보내고,
링크는 `/s#<코드>` 형태다. 카카오톡·슬랙 등이 링크를 받아 미리보기 카드를 만들 때
그 주소를 직접 가져가는데 —

```
GET /s  (facebookexternalhit UA) → HTTP 200
  og 태그: 0개
  title: ADD PLATES
  description: 없음
```

**미리보기 카드에 제목 `ADD PLATES` 만 뜨고 설명도 썸네일도 없다.**

두 가지를 같이 봐야 한다.

- 기록 자체는 **URL 프래그먼트**(`#` 뒤)에 들어 있다. 프래그먼트는 서버로 전송되지 않으므로
  **카카오톡 서버도 남의 기록을 볼 수 없다.** 이건 `docs/share-spec.md` 의 설계 의도대로
  작동하는 것이고, 바꾸면 안 되는 부분이다.
  검색엔진 쪽에서도 안전하다 — 구글은 "you can't rely on URL fragments to work with
  Googlebot", 네이버는 "수집 대상 URL 을 해석하는 과정에서 fragment 부분을 제거합니다"
  라고 적는다. **즉 공유된 개인 기록이 개별 문서로 색인될 일이 없다.**
  (일반적인 SPA 라우팅에서는 이게 치명적 결함이지만, 이 앱의 `/s#…` 에서는 오히려 방어막이다.)
- 반면 `og:title` / `og:description` / `og:image` 가 없는 것은 **의도가 아니라 누락**이다.
  이건 기록을 노출하지 않고도 채울 수 있다 (기록은 프래그먼트에, 소개는 정적 OG 태그에).

이 앱의 목표 두 개 중 하나가 *"공유 링크를 받은 사람이 '이거 뭐야'라고 묻게 만드는 것"* 인데,
지금은 그 카드가 비어 있다. **검색 노출보다 이쪽이 먼저 새고 있다.**

## 2. 구조적 제약 — 어디까지 태그로 되고 어디부터 안 되는가

### 2.1 검색엔진별 JS 렌더링 — 전부 1차 공식 문서로 확인했다

| 대상 | JS 실행 | 이 앱에 대한 판정 |
|---|---|---|
| **Googlebot** | **한다** (evergreen Chromium, 렌더 큐) | 렌더는 되지만 결과가 131자 |
| **Bingbot** | **한다** (evergreen Edge/Chromium) | 단, 공식적으로 **프리렌더 권장** |
| **네이버 Yeti** | **한다 — 단 정적 HTML 이 먼저다** | **첫 색인이 "빈 문서"로 굳을 수 있다** |
| **다음 (Daum/4.1)** | **불명 — 그러나 명시적으로 불리** | "과도한 javascript 사용"이 **공식 제외 사유** |

#### 구글

크롤링 → **렌더링** → 색인 3단계. "Googlebot queues all pages with a `200` HTTP status code
for rendering, unless a `robots` meta tag or header tells Google not to index the page."

- **지연 시간 수치는 공식 문서에 없다.** 원문은 "The page may stay on this queue for a few
  seconds, but it can take longer than that. Once Google's resources allow…" 가 전부다.
  흔히 도는 "며칠~몇 주"는 1차 근거가 없어 적지 않는다. 렌더링 타임아웃 초 수치도 없다.
- **렌더가 생략되는 조건**: robots.txt 로 JS 차단 / 비-200 응답 / `noindex` / **2MB 초과분**
  ("Any bytes that exist after that 2MB threshold are entirely ignored") / WRS 는 stateless 라
  localStorage·쿠키가 로드 간 유지되지 않음 / WebSocket 미지원 / **URL fragment(`#`) 의존 불가**.
- **이 앱은 위 조건에 걸리지 않는다.** `robots.txt` 가 없어 `/assets/index-*.js` 가 200 으로
  열리고(확인함), **148KB 로 2MB 한도에 한참 못 미친다.** 즉 렌더링은 성공할 것이다 —
  문제는 렌더 후 결과다(1.5).
- 다만 1.3 의 soft 404 가 여기서 비용이 된다. **모든 200 응답이 렌더 큐에 들어가므로**,
  존재하지 않는 주소까지 렌더링 자원을 쓰고 홈페이지 중복 문서로 쌓인다.

#### 네이버 — 이 앱에 가장 중요한 대목

네이버는 SPA 색인을 **공식적으로 지원한다고 명시한다.** 다만 **처리 순서가 구글과 다르다.**

1. JS 리소스가 아직 수집되지 않았으면 → "**정적인 HTML의 내용을 먼저 수집/분석하여 색인
   처리합니다.**"
2. JS 는 별도 과정으로 수집해 렌더링 서버에 보관
3. **재방문 시**에야 스크립트를 포함해 렌더링하고 색인 갱신 여부를 판단

**즉 첫 방문에 색인되는 것은 본문 0자짜리 빈 셸이다.** 그리고 네이버는 그런 문서를 제외
대상으로 못박는다 — "HTML 마크업이 없이 순수 자바스크립트를 활용하여 웹 페이지를 이동하는
경우… **내용이 없는 웹페이지로 간주하여 색인에서 제외하는 경우가 발생**할 수 있습니다."

네이버 공식 권장은 **SSR** 이다: "SPA 사이트라도 HTML의 주요 영역 생성은 검색로봇이 잘
인식할 수 있도록 **서버에서 렌더링(Server Side Rendering)을 처리하는 것을 권장**합니다."

그리고 등록에 관해 반드시 알아야 할 두 가지 —

- **검색 등록 절차 자체가 없다.** "네이버 웹 검색은 웹 수집 로봇이 자동으로 수집한 사이트
  정보를 반영하여 노출하고 있습니다. 따라서 **검색 등록 절차는 존재하지 않습니다.**"
  웹마스터도구 등록은 노출 조건이 아니라 **리포트를 보기 위한 것**이다.
- ⚠️ **소유확인은 자바스크립트를 지원하지 않는다.** 원문: "**소유확인은 자바스크립트 실행을
  지원하지 않으니** … `view-source:` 를 활용하시기 바랍니다." 게다가 검증 메타 태그가
  `<body>` 안에 있으면 검증에서 제외된다. → **런타임에 주입한 `naver-site-verification` 은
  100% 실패한다. 반드시 `index.html` 의 `<head>` 에 하드코딩해야 한다.** (4.0 에 반영)

Yeti UA: `… compatible; Yeti/1.1; +https://naver.me/spd …`

| `ClaudeBot` | Anthropic 모델 학습 | 크롤러 문서에 언급 없음 |
| `Claude-User` / `Claude-SearchBot` | 사용자 질문 대응 / 검색 품질 | 크롤러 문서에 언급 없음 |
| `PerplexityBot` / `Perplexity-User` | Perplexity 검색·인용 (학습에는 안 씀, 공식 명시) | 공식 언급 **없음** |
| `Google-Extended` | **크롤러가 아니다** | — |

두 가지를 짚어야 한다.

**첫째, `Google-Extended` 는 봇이 아니다.** 구글 공식 문서: "Google-Extended doesn't have a
separate HTTP request user agent string. Crawling is done with existing Google user agent
strings; the robots.txt user-agent token is used in a control capacity." 수집은 Googlebot 이
이미 하고, 이 토큰은 그 데이터를 Gemini 학습·그라운딩에 쓸지를 정하는 **스위치**다.
검색 색인·랭킹에는 영향이 없다.

**둘째, 나머지 봇들의 JS 실행 여부는 공식 문서에 아예 언급이 없다.** 대신 두 가지 근거가 있다.

- **Anthropic 1차 진술**: web fetch 도구 문서에 *"The web fetch tool currently does not support
  websites dynamically rendered with JavaScript"* 라고 명시돼 있다. 단, 이 fetch 엔진이
  `Claude-User` 크롤러와 같은 엔진인지는 문서에 없다 → 동일성은 확인 불가.
- **Vercel 실측 (2차 자료, 2024-12-17)**: nextjs.org 트래픽 로그 기준 *"none of the major AI
  crawlers currently render JavaScript"* — OpenAI·Anthropic·Perplexity·Meta·ByteDance 전부.
  JS 파일을 **다운로드는 하지만 실행하지 않는다**(ChatGPT 계열 11.50%, Claude 23.84% 요청).
  예외는 Gemini(Googlebot 인프라 사용)와 AppleBot.
  **이 측정은 21개월 전이다.** 그 사이 도입 여부는 확인하지 못했다.

### 2.3 그래서 이 앱은 어떤 상태인가

세 층으로 나뉜다.

```
① 구글 (검색 + AI Overviews / AI Mode)
   → JS 렌더링 O. 번들 148KB 로 2MB 한도에 안 걸리고 차단도 없다.
     렌더는 성공한다. 문제는 렌더 후 보이는 게 131자 로그인 화면이라는 것.
     기술적으로 가능하지만 색인할 알맹이가 없다.

② 그 외 AI 크롤러 (OpenAI · Anthropic · Perplexity)
   → JS 렌더링 안 할 가능성이 높다. 받아가는 건 0자짜리 빈 HTML.
     인용하려 해도 인용할 문장이 물리적으로 존재하지 않는다.

③ 네이버
   → JS 는 돌리지만 정적 HTML 을 먼저 색인한다. 지금 상태로 처음 수집되면
     "내용 없는 문서" 로 굳고, 네이버는 그런 문서를 색인 제외 사유로 적어 뒀다.
     현재 문서 0건인 것과 앞뒤가 맞는다.

④ Bing · 다음
   → Bing 은 돌리되 프리렌더를 권장한다. 다음은 "과도한 javascript" 를
     아예 미노출 사유로 명시한다 — 네 곳 중 가장 불리하다.
```

구글 공식 문서는 AI Overviews / AI Mode 가 **별도 인덱스가 아니라 기존 Search 인덱스를 쓴다**고
적는다 ("a page must be indexed and eligible to be shown in Google Search with a snippet").
즉 **구글 검색에 제대로 잡히는 것이 곧 구글 AI 답변 자격**이다. 두 개가 아니라 하나의 일이다.

### 2.4 메타 태그로 되는 것과 안 되는 것

| | 메타 태그만으로 | 필요한 것 |
|---|---|---|
| 공유 링크 미리보기 카드 | **완전히 해결됨** | OG 태그 5개 — 언펄러는 렌더링을 안 하고 `<head>` 만 읽는다 |
| 구글 검색 결과의 제목·설명 문구 | **해결됨** | `title` · `description` |
| 검색 결과에 **뜨는 것 자체** (랭킹) | **안 됨** | 본문 텍스트가 필요하다. 메타 태그는 순위를 만들지 않는다 |
| AI 답변 인용 (구글 외) | **안 됨** | 초기 HTML 안에 실제 문장이 있어야 한다 |
| 롱테일 질의 대응 | **안 됨** | 그 질문에 답하는 문단이 어딘가에 존재해야 한다 |

**핵심 선**: `<head>` 를 채우면 **찾아온 사람에게 잘 보이는 것**까지는 된다.
**찾아오게 만드는 것**은 `<body>` 에 읽을 문장이 있어야 시작된다.

이 구분이 중요한 이유는, 이 앱에서 메타 태그가 **무의미하지 않기 때문**이다.
1.6 의 공유 카드는 태그만으로 완전히 해결되고, 그건 이 앱의 목표 절반에 직결된다.
다만 그걸 SEO 라고 부르면 안 된다. 다른 일이다.

### 3.4 판단 — 목표 키워드에서 상위에 오를 수 있는가

**"운동 기록 앱" · "헬스 앱" · "다이어트 앱" 은 도달 불가능하다.** 솔직하게 그렇다.

- 앱 마켓 페이지 → 이 앱은 웹앱이라 스토어 등재 자체가 없다
- 보도자료 매체 → 예산 0
- 네이버 자체 UGC (블로그·카페·지식인) → 독립 도메인이 들어가는 자리가 아니다
- 기성 앱 자사 도메인 → 수년치 축적된 신호

로 채워져 있다. **메타 태그를 완벽히 채우고 본문을 넣어도 이 목록에 끼어들 수 없다.**
설령 순위를 얻어도 AI 브리핑이 위를 덮는다.

여기에 더 근본적인 문제가 있다. 이 질의를 치는 사람은 **"앱 하나 추천해줘"** 를 원한다.
그 답은 목록 기사와 리뷰 블로그의 형식이지, 앱 자신의 홈페이지 형식이 아니다.
**검색 의도와 이 사이트의 문서 형식이 애초에 맞지 않는다.**

도달 가능한 질의는 **이 앱만 답할 수 있는 구체적 조건**을 담은 것들이다. 예를 들어

- 세트 볼륨 기록 · 칼로리 없는 운동 기록

**단, 이 질의들은 검색량이 매우 작을 것이다. 실제 검색량은 확인하지 못했다** (5장).
"작은 자리를 얻는다"는 것이지 "유입이 생긴다"가 아니다.

그리고 2.2 의 귀결과 겹친다. AI 크롤러가 JS 를 안 돌린다면, AI 답변이 이 앱을 언급할 때
근거가 될 텍스트는 **이 앱을 서술한 제3자 문서**에서 올 수밖에 없다.
(이 메커니즘을 직접 명시한 1차 공식 문서는 찾지 못했다 — 확인된 사실들에서 나온 추론이다.)

**지금 그 조건을 이미 만족하는 문서가 하나 있다.**

```
https://github.com/builder-glen/add-plates   (public, 200 OK)
```

GitHub 은 README 를 **서버에서 HTML 로 렌더해 준다.** 확인했다 — 저장소 페이지 원본 HTML

AI 크롤러도 이 문서는 읽을 수 있다.** 현재 웹 전체에서 이 프로젝트에 대해
**크롤러가 읽을 수 있는 유일한 한국어 텍스트**다.

그런데 그 저장소에 두 가지 문제가 있다. 확인한 사실이다.

## 4. 선택지 — 작업량 순

> 각 항목은 **하라는 권고가 아니라 재료**다. 실익과 한계를 같이 적었다.

### 4.0 (0단계) 먼저 사실을 확보한다 — 10분, 코드 변경 없음

1.4 에서 구글 색인 여부를 확인하지 못했다. 판단의 전제이므로 이것부터 채우는 게 맞다.

- **Google Search Console** 에 `add-plates.dev` 등록 → 색인 여부, 실제 유입 질의,
  **렌더링 결과 스크린샷(URL 검사 도구)** 까지 한 번에 나온다. 1.5 의 "렌더링해도 131자"가
  실제로 그런지 눈으로 확인할 수 있다. 추정이 필요 없어진다.
- **네이버 서치어드바이저** 등록 → 네이버는 현재 문서 0건임을 확인했다(1.4).
  단, 2.1 에서 확인했듯 **네이버에 "검색 등록 절차"는 존재하지 않는다.** 등록해야 노출되는
  게 아니라, 등록하면 수집·색인 리포트를 볼 수 있는 것이다. 목적은 노출이 아니라 관측이다.
- 브라우저에서 `site:add-plates.dev` 직접 검색.

> ⚠️ **네이버 소유확인에는 함정이 있다.** 네이버는 "소유확인은 자바스크립트 실행을 지원하지
> 않는다"고 명시하고, 검증 메타 태그가 `<body>` 안에 있으면 검증에서 제외한다.
> → `naver-site-verification` 을 **`index.html` 의 `<head>` 에 직접 써야 한다.**
> React 안에서 런타임에 주입하면 반드시 실패한다. (구글은 HTML 파일 업로드 방식도 되는데,
> 이 앱은 `public/` 에 파일을 두면 SPA 폴백보다 우선하므로 그 방식도 작동한다.)

**실익**: 이후 모든 판단의 근거가 생긴다. **한계**: 노출이 늘지는 않는다.

### 4.1 저장소 링크 고치기 — 5분, 코드 변경 없음

`homepage` 를 `https://add-plates.dev` 로, `topics` 에 몇 개 추가.

**실익**: 죽은 링크를 고친다. 3.6 에서 봤듯 GitHub 저장소는 현재 유일하게 크롤러가 읽을 수 있는
문서이고, 그 문서에서 사이트로 가는 유일한 링크가 지금 404 다. 비용 대비 가장 명확하다.
**한계**: 검색 순위를 만들지 않는다. 링크가 링크로 기능하게 될 뿐이다.

### 4.2 `<head>` 채우기 + `robots.txt` / `sitemap.xml` — 30분, `index.html` 과 `public/` 만

- `description`, `canonical`, OG 5종(`og:title`·`description`·`image`·`url`·`type`),
  `twitter:card`
- `public/robots.txt`, `public/sitemap.xml` (실제 파일을 두면 SPA 폴백보다 우선한다 —
  `manifest.webmanifest` 가 정상 서빙되는 것으로 확인했다)

**실익**: **1.6 의 공유 카드 문제가 완전히 해결된다.** 언펄러는 JS 를 안 돌리고 `<head>` 만
읽으므로, 이건 정적 SPA 라는 제약을 전혀 받지 않는다. 지금 막 나간 공유 기능의 실효가 달라진다.
`robots.txt` 자리에서 HTML 이 나가는 상태도 정리된다.

**한계**: **검색 순위에는 거의 영향이 없다.** 본문이 여전히 0자이기 때문이다.
이건 SEO 작업이 아니라 **공유 기능 마감 작업**으로 보는 게 정확하다.

> 주의: `og:image` 는 절대 주소여야 하고, 공유 링크(`/s#…`)에도 같은 정적 카드가 붙는다.
> 기록 내용은 프래그먼트에 있어 서버로 안 가므로 **개인 기록이 카드에 새지 않는다** — 유지된다.

### 4.3 초기 HTML 에 본문 텍스트 넣기 — 1~2시간, `index.html` 만

`index.html` 자체에 이 앱이 무엇인지 설명하는 실제 한국어 문단을 넣는다. 두 방식이 있다.

- **`<noscript>` 블록** — 안전하다. 다만 검색엔진이 `<noscript>` 에 주는 비중은 낮다고 알려져
  있고, 이 앱은 정확한 취급을 **확인하지 못했다**.
- **`<div id="root">` 안에 미리 채워 두기** — `createRoot().render()` 가 마운트할 때 컨테이너
  내용을 지우므로 사용자는 못 보고 크롤러는 본다.
  **위험**: 넣은 내용이 실제 화면과 크게 다르면 구글 정책상 **클로킹**으로 볼 수 있다.
  참고로 Bing 은 프리렌더링을 공식 권장하면서 "as long as you make a good faith effort to
  return the same content to all visitors" 면 클로킹이 아니라고 명시한다 — **판단 기준은
  "같은 내용을 주는가"**다. 로그인 화면이 실제로 말하는 것과 같은 내용만 넣는다면 위험이
  낮다. 다만 **경계가 어디인지는 판단의 영역**이고, 밀어붙일 문제가 아니다.

이 선택지는 네이버에서 특히 값이 크다. 2.1 에서 봤듯 네이버는 **정적 HTML 을 먼저 색인**하고
재방문 후에야 렌더링한다. 지금 상태로 처음 수집되면 "내용 없는 문서"로 굳는데, 초기 HTML 에
문단이 들어 있으면 **첫 수집부터 제대로 된 문서로 잡힌다.** 아직 네이버에 0건이라는 것은
뒤집어 말하면 **아직 나쁜 첫인상이 굳지 않았다**는 뜻이기도 하다.

여기서 1.5 의 문제도 같이 손댈 수 있다 — `<title>` 이 `ADD PLATES` 뿐이고 한국어가 없다.

**실익**: JS 를 안 돌리는 AI 크롤러(OpenAI·Anthropic·Perplexity)가 처음으로 읽을 게 생긴다.
구글에도 매칭할 단어가 생긴다. **정적 SPA 라는 제약을 실제로 우회하는 가장 싼 방법**이다.
**한계**: 한 페이지 분량의 텍스트로 3.4 의 head 키워드에 들어가지는 못한다. 3.5 의 롱테일이 상한이다.

### 4.4 로그인 앞에 공개 소개 화면 두기 — 반나절~1일, 제품 변경

지금은 `!session → LoginScreen` 이다. 그 앞에 로그인 없이 볼 수 있는 소개 화면을 둔다.

**실익**: 크롤러와 사람에게 동시에 답이 된다. 클로킹 논란이 없다(보이는 것과 색인되는 것이 같다).
공유 링크를 받은 사람의 "이거 뭐야"에도 이 화면이 답한다.
**한계**: **제품 결정이다.** 지금 로그인 화면은 131자로 끝나는 절제된 화면이고
(`봉은 조상이 들이주지 않는다`), 소개 화면을 앞에 두면 그 톤이 바뀐다.
이건 마케팅이 정할 일이 아니다. 판단 재료로만 남긴다.
그리고 이것만으로는 **여전히 JS 렌더링에 의존**한다 — 4.3 과 같이 가야 AI 크롤러에 닿는다.

### 4.5 제3자 문서 만들기 — 글 쓰는 시간, 코드 변경 0

3.6 의 결론에 정면으로 대응하는 유일한 선택지다. 한국 검색에서 이 질의들의 상위는 남의 글이고,
AI 답변의 인용 근거도 제3자 문서다.

이 프로젝트가 실제로 가진 재료가 있다 — **칼로리를 왜 뺐는가**(2024 스코핑 리뷰, 효율 상수
4~43% 편차), **세부 부위를 왜 근거 있는 것만 넣었는가**, **서버를 왜 안 만들었는가**(RLS),
**기록을 링크에 담아 저장하지 않는 공유 설계**. 전부 README 와 `docs/` 에 이미 정리돼 있다.

이건 앱 홍보 글이 아니라 **판단 기록**이고, 3.4 에서 본 "앱 추천 목록" 형식과 경쟁하지 않는다.
포트폴리오 목적과도 정확히 겹친다 — 채용 담당자가 반응하는 것은 앱 순위가 아니라 이 판단들이다.

**실익**: 크롤 가능하고(전부 서버 렌더 플랫폼), 인용 가능하고, 롱테일 질의에 실제로 답한다.
**한계**: 시간이 든다. 글이 읽히리라는 보장이 없다. **어느 채널에 어떤 글을 쓸지는 별도 논의**이고,
지시받지 않았으므로 여기서 정하지 않는다.

### 4.6 SSR / 정적 프리렌더 도입 — 며칠, 구조 변경

`package.json` 은 순수 Vite + React 다. 라우터도 없고(`window.location.pathname === '/s'` 분기),
SSR 프레임워크도 없다. 서버 렌더를 하려면 Next 등을 도입하거나 프리렌더 파이프라인을 붙여야 한다.

**실익**: 모든 크롤러에 완전한 HTML 을 준다. 2.2 의 제약이 근본적으로 사라진다.
**네 엔진 전부가 공식적으로 이걸 권장한다** — 네이버는 "SSR 을 처리하는 것을 권장",
Bing 은 "we recommend dynamic rendering", 다음은 과도한 JS 를 미노출 사유로 적는다.
**교과서적으로는 이게 정답이다.**

**한계**: **README 가 자랑하는 "서버를 만들지 않았다"는 설계 판단과 정면으로 충돌한다.**
운영비 $0, RLS 로 권한을 데이터 옆에 둔 구조가 이 프로젝트의 서사인데, SEO 때문에 서버를 들이면
포트폴리오로서의 이야기가 약해진다. 그리고 3.4 에서 봤듯 **SSR 을 해도 head 키워드에는 못 들어간다** —
얻는 것은 여전히 롱테일 몇 개다. **얻는 것에 비해 잃는 것이 크다고 본다.**
4.3 이 같은 문제의 대부분을 훨씬 싸게 해결한다.

> 정확히 말하면 이건 SEO 문제가 아니라 **트레이드오프 문제**다. "권장 사항이니 해야 한다"가
> 아니라 "권장 사항인 걸 알면서 안 하기로 한다"가 이 프로젝트의 일관된 태도에 맞는다.
> 칼로리를 뺀 결정과 같은 종류의 판단이다. 결정은 사용자가 한다.

## 5. 모른다고 남기는 것

확인하지 못한 것을 아는 것처럼 쓰지 않았다. 목록은 다음과 같다.

**색인 상태**
- **구글이 `add-plates.dev` 를 색인했는가** — 확인 실패. `curl` 로는 JS 셸만 오고, 대조군으로
  방법 자체가 무효임을 확인했다. → 4.0 의 Search Console 로 해결된다.
- **Bing 색인 여부** — 봇 차단으로 확인 실패.
- 네이버는 확인했다 (문서 0건).

**크롤러 동작**
- **AI 크롤러(GPTBot·OAI-SearchBot·ClaudeBot·PerplexityBot)의 JS 실행 여부** — **어느 공식
  문서에도 언급이 없다.** 근거는 Anthropic 의 web fetch 문서 1차 진술과 Vercel 2차 실측뿐이고,
  Vercel 측정은 **2024-12 로 21개월 전**이다. 그 사이 도입 여부는 모른다.
- **Anthropic 의 web fetch 엔진과 `Claude-User` 크롤러가 같은 엔진인지** — 문서에 없다.
- **다음 `Daum/4.1` 이 JS 를 실행하는가** — 명시 문서가 없다. "과도한 javascript 사용 시
  분석이 어렵다"는 서술로 보아 역량이 제한적이라 **추정**할 뿐, 단정하는 문장은 없다.
- **네이버 Yeti 의 렌더링 엔진 종류·버전, evergreen 여부, 재방문 주기** — 공식 미공개.
  → **네이버 문서 0건의 원인은 좁혀졌다.** JS 미실행 때문은 아니다(Yeti 는 실행한다).
    남은 후보는 (a) 정적 HTML 우선 정책 + 본문 0자 → 색인 제외, (b) 신규 도메인이라 아직
    수집 전. **둘 중 어느 쪽인지는 서치어드바이저 등록(4.0) 후 수집 리포트로 확인된다.**

**렌더링 세부**
- **구글의 크롤 → 렌더 지연이 얼마인지** — "Once Google's resources allow" 가 전부다.
  **1차 문서에 수치가 없다.** 흔히 도는 "며칠" 숫자는 근거를 확인하지 못해 적지 않았다.
- **구글 렌더링 타임아웃 초 수치** — 공식 문서에 없다. (도는 "5초"는 비공식)
- **Googlebot Chromium 의 구체 버전** — evergreen 이라는 것만 공개.
- **Bing 의 렌더 큐·지연·타임아웃** — 공식 문서 없음. 또 "프레임워크를 전부 지원하지는
  않는다"는 2018년 진술이 2026년에도 유효한지 재확인하는 최신 문서가 없다.
- **`<noscript>` 콘텐츠를 각 엔진이 색인에 얼마나 반영하는지** — 확인하지 못했다. 4.3 의 선택에 영향.

**키워드·수요**

  이 문서에 검색량 숫자를 한 개도 쓰지 않은 이유다.
- **순위** — 3.2~3.5 의 숫자는 **결과 페이지의 도메인 등장 횟수**이지 순위가 아니다.
  스크립트·이미지 URL 이 섞여 있고, 로그인·지역·개인화에 따라 결과가 달라진다.

  결과 대부분이 내부 문서라는 3.2 의 관찰은 했지만, 구조적 정책인지 이 질의들의 특성인지
