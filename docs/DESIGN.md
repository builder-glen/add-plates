## 1. 제품 정의

### 한 줄 정의
헬스장에서 **지난번 기록을 보면서** 오늘 운동을 기록하는 모바일 웹앱.

### 해결하는 문제
운동 기록을 메모장·엑셀·기억에 흩어서 관리하다 보니
"지난주에 벤치프레스 몇 kg 들었지?"를 바 앞에 서서 못 떠올린다.

### 메모장 대비 차별점 (= 이 제품의 존재 이유)
1. **직전 기록 자동 노출** — 종목을 고르는 순간 지난번 세트가 뜬다
2. **초성 검색** — 장갑 낀 손으로 "ㅂㅊㅍ" 3타에 벤치프레스 선택
3. **구조화된 데이터** — 나중에 부위별 볼륨·중량 추이 분석 가능

## 2. 확정된 의사결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 사용자 범위 | 초기 나 혼자 → 지인 확대 | 처음부터 `user_id` 스코프 + 인증 전제 |
| 기록 최소 단위 | **세트 단위** (종목 요약 ✕) | 세트마다 중량이 다른 실제 운동 표현 |
| MVP 범위 | 기록 CRUD + **직전 기록 표시** | 차별점 확보를 위한 최소 범위 |
| 종목 유형 | 웨이트 + 맨몸 2종 | 보디빌딩식 트레이닝 커버. 유산소는 후속 |

### MVP에서 명시적으로 **제외**하는 것
- 루틴/템플릿 (등 데이 루틴 저장) → v2
- 통계·차트·1RM 계산 → v2
- 유산소/시간 기반 종목 → v2 (스키마 확장 포인트만 확보)
- 소셜·공유·기록 비교 → v3
- 운동 타이머, 휴식 알림 → 후순위

## 3. 기술 스택 (제안)

| 레이어 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js 15 (App Router) + TypeScript | Vercel 배포 원클릭, 모바일 웹 최적 |
| DB + 인증 | **Supabase** (Postgres + Auth + RLS) | "나 혼자 → 지인 확대" 경로에 최적. 인증·권한을 직접 안 짜도 됨 |
| 스타일 | Tailwind CSS + shadcn/ui | 바텀시트·폼 컴포넌트 즉시 사용 |
| 배포 | Vercel | |
| 앱 형태 | PWA (홈 화면 추가) | 앱스토어 심사 없이 앱처럼 사용 |

> **RLS(Row Level Security)** — DB가 행 단위로 "이 사용자는 이 행만 볼 수 있다"를 강제하는 Postgres 기능.
> API 코드에서 `where user_id = ...`를 빠뜨려도 DB가 막아준다. 지인 확대 시 데이터 유출 사고를 구조적으로 방지.

## 4. 데이터 모델

### 4.1 구조 개요

```
workout_sessions (하루의 운동)
└── workout_entries (그날 한 종목)      → exercises (종목 마스터) 참조
    └── workout_sets (세트 하나)         ← 최소 기록 단위
```

### 4.2 스키마

```sql
-- 운동 부위
create type muscle_group as enum (
  'chest','back','shoulder','leg','biceps','triceps','core','etc'
);

-- 기록 방식 (MVP 2종, 후속 확장 지점)
create type tracking_type as enum (
  'weight_reps',      -- 중량 × 횟수 (벤치프레스)
  'bodyweight_reps'   -- 횟수만    (풀업)
);

-- ── 종목 마스터 ────────────────────────────────
create table exercises (
  id            uuid primary key default gen_random_uuid(),
  name          text not null,                       -- '벤치프레스'
  chosung       text not null,                       -- 'ㅂㅊㅍㄹㅅ' (저장 시 자동 계산)
  aliases       text[] not null default '{}',        -- {'벤프','bench press'}
  muscle_group  muscle_group not null,
  equipment     text,                                -- 바벨/덤벨/머신/케이블/맨몸
  tracking_type tracking_type not null default 'weight_reps',
  owner_id      uuid references auth.users(id),      -- null = 공용 기본 종목
  created_at    timestamptz not null default now()
);
create unique index on exercises (coalesce(owner_id::text,'global'), name);

-- ── 운동 세션 (하루 복수 허용) ──────────────────
create table workout_sessions (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references auth.users(id),
  performed_on date not null,
  title        text not null,                       -- '오전 운동' (생성 시각 기준 자동 부여)
  started_at   timestamptz not null default now(),  -- 같은 날 세션 정렬 기준
  memo         text,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);
create index on workout_sessions (user_id, performed_on, started_at);

-- ── 세션 안의 종목 ─────────────────────────────
create table workout_entries (
  id          uuid primary key default gen_random_uuid(),
  session_id  uuid not null references workout_sessions(id) on delete cascade,
  exercise_id uuid not null references exercises(id),
  order_index int  not null,                      -- 그날의 종목 순서
  created_at  timestamptz not null default now()
);
create index on workout_entries (session_id);
create index on workout_entries (exercise_id);   -- 직전 기록 조회용

-- ── 세트 (최소 기록 단위) ───────────────────────
create table workout_sets (
  id        uuid primary key default gen_random_uuid(),
  entry_id  uuid not null references workout_entries(id) on delete cascade,
  set_no    int  not null,                        -- 1,2,3...
  weight_kg numeric(5,1),                         -- 맨몸 종목이면 null
  reps      int  not null check (reps > 0),
  unique (entry_id, set_no)
);
```

### 4.3 설계 판단 노트

**종목-부위는 1:1 (`muscle_group` 단일값)**
벤치프레스는 가슴(주동근) + 삼두·전면삼각(협응근)을 쓰지만, MVP에서는 주동근만 저장한다.
협응근까지 넣으면 다대다 테이블이 필요한데, 그 값어치는 "부위별 볼륨 정밀 분석"(v2 통계)에서야 생긴다.

**`chosung`은 계산 컬럼이 아니라 저장 컬럼**
종목명이 바뀔 일이 거의 없고, 저장 시 한 번 계산해두면 클라이언트가 그대로 읽어 쓴다.

**맨몸 종목의 `weight_kg`는 `null`**
0이 아니라 null. "가중 없이 수행"과 "중량 0kg"을 구분할 필요는 없지만,
나중에 가중 풀업(+10kg)을 지원할 때 null/값 구분이 그대로 쓰인다.

## 5. 해소된 쟁점 (2026-09-02 확정)

### 5.1 하루 2회 운동 → **복수 세션 허용**
`unique(user_id, performed_on)` 제약을 제거하고 `title`·`started_at`을 추가했다.
Glen이 아침 유산소 / 저녁 웨이트를 분리 기록하기 때문.

탭 depth를 늘리지 않기 위해 `날짜 → 세션 목록 → 상세` 3단으로 가지 않고,
**한 날짜 화면에 세션을 섹션으로 이어 붙인다** (7.2 참조).
`title`은 생성 시각으로 자동 부여하며 사용자에게 입력을 강제하지 않는다.

### 5.2 기본 종목 목록 → **9절 초안 그대로 사용**
실사용하며 커스텀 종목 추가(PRD F-07)로 보완한다.

### 5.3 인증 방식 → **구글 OAuth 단일**
카카오는 디벨로퍼스 앱 등록·비즈앱 전환·동의항목 검수까지 초기 공수가 크고,
대상이 지인 10명 규모라 실익이 낮다. 필요 시 Supabase에서 프로바이더만 켜면 된다.

### 5.4 인프라 → **Supabase Free + Vercel Hobby (월 $0)**
AWS는 이 규모에 과하다. Neon·Cloudflare D1은 DB는 저렴하지만 인증을 직접 구현해야 한다.

**⚠️ 무료 플랜 함정** — Supabase는 7일간 DB 활동이 없으면 프로젝트를 일시정지한다.
Vercel Cron으로 3일 주기 워밍업 쿼리를 배포에 포함한다 (PRD F-08).

## 6. 핵심 기능 설계

### 6.1 초성 검색

**알고리즘 — 한글 초성 추출**

한글 완성형 글자는 `초성×588 + 중성×28 + 종성` 규칙으로 인코딩되어 있어 계산으로 초성을 뽑는다.

```ts
const CHO = ['ㄱ','ㄲ','ㄴ','ㄷ','ㄸ','ㄹ','ㅁ','ㅂ','ㅃ','ㅅ','ㅆ',
             'ㅇ','ㅈ','ㅉ','ㅊ','ㅋ','ㅌ','ㅍ','ㅎ'];

export function toChosung(text: string): string {
  return [...text].map(ch => {
    const code = ch.charCodeAt(0) - 0xAC00;      // '가' = 0xAC00
    return code >= 0 && code <= 11171 ? CHO[Math.floor(code / 588)] : ch;
  }).join('');
}
// toChosung('벤치프레스') === 'ㅂㅊㅍㄹㅅ'
```

**검색 위치: 클라이언트 메모리**

종목 마스터는 200~300개 규모다. 앱 시작 시 전량 로드해 메모리에서 필터한다.

- 서버 왕복 0 → 타이핑 즉시 반응 (디바운스 불필요)
- 오프라인에서도 검색 동작
- 코드가 단순 (검색 API·인덱스·페이지네이션 전부 불필요)

종목이 1,000개를 넘어가면 그때 서버 검색으로 전환한다. MVP에서는 과설계.

**매칭 규칙 3종**

| 입력 | 매칭 방식 | 결과 |
|---|---|---|
| `ㅂㅊㅍ` | 초성 부분 매칭 | 벤치프레스 |
| `벤치` | 이름 부분 매칭 | 벤치프레스, 인클라인 벤치프레스 |
| `벤프` | 별칭 매칭 | 벤치프레스 |

**정렬 우선순위** (같은 점수면 최근 사용순)

```
1. 이름 완전 일치
2. 이름 앞부분 일치      "벤치"  → 벤치프레스
3. 초성 앞부분 일치      "ㅂㅊㅍ" → 벤치프레스
4. 별칭 일치            "벤프"  → 벤치프레스
5. 이름 중간 포함        "프레스" → 벤치프레스, 숄더프레스
6. 초성 중간 포함
```

**MVP 제외**
- 혼합 입력 (`벤ㅊㅍ`) — 구현 복잡도 대비 사용 빈도 낮음
- 쌍자음 관대 매칭 (`ㄱ`으로 `ㄲ` 찾기) — 종목명에 쌍자음 초성이 거의 없음

### 6.2 직전 기록 표시

종목을 선택하면 **그 종목의 가장 최근 기록**을 세트 입력란에 회색 placeholder로 띄운다.

```sql
-- 사용자 $1이 종목 $2를 마지막으로 한 날의 전체 세트
with last_session as (
  select s.id, s.performed_on
  from workout_sessions s
  join workout_entries e on e.session_id = s.id
  where s.user_id = $1
    and e.exercise_id = $2
    and s.performed_on < $3        -- 오늘 세션은 제외
  order by s.performed_on desc
  limit 1
)
select ls.performed_on, st.set_no, st.weight_kg, st.reps
from last_session ls
join workout_entries e on e.session_id = ls.id and e.exercise_id = $2
join workout_sets   st on st.entry_id  = e.id
order by st.set_no;
```

UI 표현:
```
벤치프레스                    지난 기록 · 8/15 (7일 전)
  1세트  [ 60 ]kg × [ 10 ]회     이전: 60kg × 10
  2세트  [    ]kg × [    ]회     이전: 70kg ×  8   [← 그대로 채우기]
```

### 6.3 세트 복사

세트 추가 시 **직전 세트의 중량·횟수를 기본값으로 채운다.**
3세트 × 같은 중량이면 `[+세트]` 두 번으로 입력 끝. 세트별 기록의 입력 부담을 여기서 해소한다.

## 7. 화면 설계

### 7.1 화면 목록 (3개)

| 화면 | 역할 |
|---|---|
| **홈 (일자별 기록)** | 날짜 선택 + 그날의 종목·세트 목록 + 편집 |
| **종목 선택 시트** | 초성 검색 + 부위 탭 + 최근 사용 종목 |
| **설정** | 로그인/로그아웃, 커스텀 종목 관리 |

세트 입력은 별도 화면 없이 홈의 종목 카드 안에서 인라인 편집한다.
(헬스장에서 세트 사이 30초 안에 끝나야 하므로 화면 전환 최소화)

### 7.2 홈 화면 레이아웃

```
┌─────────────────────────────┐
│  ‹  9월 2일 (수)  ›    [달력] │   ← 날짜 스트립, 좌우 스와이프
├─────────────────────────────┤
│ ▸ 오전 운동          09:12 ⋮ │   ← 세션 헤더 (1세션이면 눈에 안 띄게)
│   🟥 벤치프레스         ⋮    │
│      1세트  60kg × 10  ✓    │
│      2세트  70kg ×  8  ✓    │
│      3세트  [  ]kg × [ ]    │
│      + 세트 추가             │
│   [ + 운동 추가 ]            │
├─────────────────────────────┤
│ ▸ 오후 운동          19:40 ⋮ │
│   🟦 랫풀다운           ⋮    │
│      1세트  50kg × 12  ✓    │
│   [ + 운동 추가 ]            │
├─────────────────────────────┤
│      [ + 세션 추가 ]         │
└─────────────────────────────┘
```
좌측 색상 바 = 부위 구분. 기록이 없는 날은 빈 상태 + `[+ 운동 추가]`만
(첫 종목 추가 시 세션이 자동 생성된다).

### 7.3 종목 선택 시트

```
┌─────────────────────────────┐
│ 🔍 ㅂㅊㅍ                    │
├─────────────────────────────┤
│ 전체 │ 가슴 │ 등 │ 어깨 │ ...│   ← 부위 탭
├─────────────────────────────┤
│ 벤치프레스          가슴·바벨 │
│ 인클라인 벤치프레스  가슴·바벨 │
│ 덤벨 벤치프레스     가슴·덤벨 │
├─────────────────────────────┤
│ + '벤치프레스' 직접 추가      │   ← 검색 결과 없을 때
└─────────────────────────────┘
```
검색어가 비어 있으면 **최근 사용 종목 10개**를 먼저 보여준다.

## 8. 동작 명세 (End-to-End)

### 8.1 운동 기록 추가

```
[+ 운동 추가] 탭
  → 종목 선택 시트 오픈 (종목 마스터는 이미 메모리에 로드됨)
  → "ㅂㅊㅍ" 입력 → 메모리 필터 (서버 호출 없음) → 결과 렌더
  → [벤치프레스] 탭
  → 해당 날짜에 세션이 없으면
      POST /api/sessions { performed_on, title: 자동생성 } → 201 { session_id }
  → POST /api/entries { session_id, exercise_id, order_index } → 201 { entry_id }
  → GET /api/exercises/{id}/last-record → 200 { performed_on, sets[] }
  → 시트 닫힘 + 종목 카드 렌더 + 1세트 행에 직전 기록 placeholder 표시
```

### 8.2 세트 입력

```
1세트 중량/횟수 입력 → 입력란 blur 또는 [✓] 탭
  → POST /api/sets { entry_id, set_no, weight_kg, reps } → 201
  → 해당 행 확정 상태(✓)로 전환 + 다음 세트 행 자동 생성
     (직전 세트 값이 기본값으로 채워짐)
```

낙관적 업데이트(Optimistic Update)를 적용한다 — UI를 먼저 갱신하고 서버 응답을 기다린다.
실패 시 행을 빨간 테두리 + [재시도]로 표시. 헬스장 지하 통신 환경을 전제로 한 설계.

### 8.3 수정 / 삭제

```
세트 값 탭 → 인라인 편집 → blur → PATCH /api/sets/{id} → 200

종목 카드 [⋮] → [삭제] → 확인 다이얼로그 → DELETE /api/entries/{id} → 204
  → 하위 workout_sets 는 ON DELETE CASCADE 로 함께 삭제
  → 스낵바 "삭제됨 [실행취소]" 5초 노출
```

세션의 마지막 종목을 삭제하면 빈 세션이 남는다.
→ 빈 세션은 조회 시 무시하고, 별도 정리 배치는 두지 않는다 (비용 대비 실익 없음).
→ 단, 하루에 세션이 2개 이상일 때는 빈 세션 헤더를 숨겨 화면을 어지럽히지 않는다.

## 10. 구현 순서

```
1. Supabase 프로젝트 + 스키마 + RLS 정책      → 검증: 다른 계정으로 남의 기록 조회 시 0건
2. 종목 마스터 시드 (50개) + toChosung 유닛테스트 → 검증: 'ㅂㅊㅍ'→벤치프레스 테스트 통과
3. 로그인 (구글/카카오 OAuth)                → 검증: 로그인→홈 랜딩, 새로고침 세션 유지
4. 홈 화면 + 날짜 이동 + 세션 조회            → 검증: 기록 있는 날/없는 날 렌더 확인
5. 종목 선택 시트 + 초성 검색                 → 검증: 3종 매칭 규칙 각각 동작
6. 세트 CRUD (인라인 편집 + 낙관적 업데이트)   → 검증: 오프라인 전환 시 재시도 UI 노출
7. 직전 기록 표시                            → 검증: 2개 날짜 기록 후 placeholder 정확도
8. PWA 설정 + Vercel 배포                    → 검증: 폰 홈 화면 추가 후 실제 헬스장 사용
```
